# sentry-docker

## 项目定位

自托管 Sentry 部署项目，面向内网或受限网络环境，提供错误监控、性能追踪、事件存储、ClickHouse 清理、资源配置和一键启动能力。

## 关键问题

- 内网环境部署 Sentry 需要解决 Docker Compose 编排、服务依赖、消费者配置、ClickHouse 存储清理和资源限制。
- 受限网络环境容易因外网功能、兼容性服务或默认消费者导致超时和资源浪费。
- 前端多项目接入 Sentry 后，需要稳定的自托管服务作为错误收集基础。

## 我的动作

- 搭建自托管 Sentry Docker Compose 配置，补充 relay、nginx、Kafka topic 初始化和相关配置文件。
- 增加 Snuba/Sentry 多消费者配置，优化 relay/nginx 健康检查和消费者内存限制。
- 添加 ClickHouse TTL、清理脚本和日志配置，控制事件数据存储增长。
- 增加离线环境一键启动脚本，禁用不兼容或不需要的服务，删除过时同步脚本。
- 补充 README 架构组件、资源优化、用户添加说明和内网服务名配置。

## 结果与提效

- 形成可在内网环境部署的 Sentry 基础设施，支撑前台、后台和微信端错误上报。
- 通过消费者资源限制、ClickHouse TTL 和无用服务禁用降低运行成本和超时风险。
- 一键启动脚本和 README 降低后续部署和交接成本。
- 具体提效需补充部署耗时、资源占用、错误事件量和问题定位时间。

## AI 如何提效

- 自托管 Sentry 涉及 Docker Compose、ClickHouse、Snuba、Relay、Nginx 和内网限制，适合用 AI 辅助做配置差异排查、服务依赖梳理和文档整理。
- 当前可验证结果是 README、配置和脚本持续沉淀；具体 AI 是否参与排障仍缺少协作记录，标记为“待补充证据”。

## 可复用经验

- 自托管监控系统要同时考虑部署、存储、消费者、网络、资源和文档，不只是把服务跑起来。
- 内网环境要主动禁用外网依赖，避免默认功能造成超时。
- ClickHouse 等事件存储必须设计清理策略，否则长期运行风险会逐步放大。
