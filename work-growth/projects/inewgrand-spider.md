# inewgrand-spider

## 项目定位

住建部企业资质运维后端服务，面向全国建筑市场监管公共服务平台公开数据，目标是建立企业资质、注册人员、资质规则比对、证书到期预警和通知能力的后端底座。

## 目标

- 工程目标：用 Node.js + TypeScript + NestJS + Fastify 建立纯后端采集服务，不引入不必要的前端框架。
- 业务目标：为企业资质资格、注册人员信息、资质标准比对和预警能力准备可持续采集的数据入口。
- 效率目标：把住建部详情页打开、验证码验证、token 刷新、接口请求、解密和结果保存流程自动化，减少人工重复操作。

## 背景问题

- 目标页面接口依赖浏览器会话 `accessToken`，接口返回 408 后需要重新验证。
- 详情接口返回十六进制 AES-CBC 密文，需要按官网前端口径解密后才能沉淀数据。
- GeeTest 验证码包含图标顺序点选等复杂形态，单纯 HTTP 请求无法覆盖真实采集链路。
- 后续资质比对、人员预警和通知能力需要清晰模块边界，避免采集逻辑和业务规则混在一起。

## 工具/技术/方法

- 后端框架：Node.js、TypeScript、NestJS、Fastify adapter、pnpm。
- 自动化采集：Playwright 浏览器会话、接口响应监听、token 抽取、408 后刷新与重试。
- 验证码能力：OpenCV、Sharp、OpenAI SDK 兼容 DashScope、验证码 Solver/Recognizer/Actuator 分层。
- 工程质量：Jest、ts-jest、ts-node、ESLint、Prettier、`.env.example`、环境变量校验。
- 协作方法：项目级 `AGENTS.md` 约束最小改动、pnpm、测试、环境变量和数据合规规则。

## 关键动作

- 初始化 NestJS 后端骨架，预留 crawler、qualification、personnel、compliance、warning、notification、jobs 等模块。
- 实现健康检查、环境变量校验、住建部 crawler controller/service 和基础单元测试。
- 引入 3D 物体语义点选验证码基础模块，补充提示解析、规则引擎、对象检测和求解测试。
- 建立验证码统一调度架构，把滑块、旋转、单点、顺序点选、文字点选拆成可扩展 Solver。
- 用 Playwright 建立浏览器会话服务，监听目标接口、桥接验证码、刷新 accessToken，并在接口 408 时自动重试一次。
- 接入 Qwen VLM，补充 provider、点选 recognizer、prompt、JSON 容错、index 顺序重排和相关测试。
- 保存接口原始数据和解密结果到 `docs`，并新增 `crawl-company` 端到端 smoke 脚本。
- 针对“重新验证”按钮主动轮询，覆盖首次进入或会话久未访问时页面不主动发 API 的场景。
- 记录 GeeTest 图标顺序点选的实战经验，并清理一次性企业数据 JSON，避免样本文件长期留在文档目录。

## 结果与提效

- 从 0 到 1 建立后端工程、采集模块、验证码模块、测试和脚本入口。
- 将“页面验证 -> 获取 token -> 请求接口 -> 解密 -> 保存结果”的链路沉淀为服务方法和脚本，而不是一次性手工操作。
- 验证码能力从单点能力扩展为可插拔调度架构，并补充 Qwen VLM 点选识别经验；后续替换 VLM、OCR、OpenCV 或动作执行层时不需要重写主流程。
- 具体采集成功率、验证码通过率、单次耗时和重试次数仍需后续运行数据验证。

## 可复用经验

- 爬虫或采集服务不应只关注接口请求，还要把浏览器会话、验证码、token 生命周期、加密解密、失败重试和日志留痕一起纳入设计。
- 验证码识别要拆分为识别、求解和执行动作三层，避免模型替换或页面动作变化时牵动整个流程。
- 环境变量新增必须同步 `.env.example` 和测试，降低脚本、服务和 CI 环境之间的配置差异。
- 复杂外部平台接入需要写流程文档和排障记录，否则“能跑一次”的经验很难被稳定复现。
